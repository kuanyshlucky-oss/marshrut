# JetisHub — API (Go + PostgreSQL)

REST-бэкенд платформы «JetisHub»: аккаунты (выдаёт администратор), профиль,
избранное, **тесты с проверкой ответов на сервере** (профильные предметы, английский,
ТГО, симуляция КТ), статистика по темам, выдача доступа к тестам по направлению и
языку (RU/KZ), справочники и дорожная карта «МагистрТрек».

- **Go** (стандартный `net/http`), почти без зависимостей: `pgx`, `x/crypto`
- **PostgreSQL** (Neon); пароли — bcrypt; токены — HMAC + серверная сессия
- **Docker** → Render

## Архитектура

```
cmd/api/main.go          только сборка зависимостей и запуск (graceful shutdown)
internal/
  config/                настройки из окружения + проверка (слабые секреты = отказ запуска)
  auth/                  пароли (bcrypt), токены (HMAC), кэш сессий
  content/               банки вопросов (go:embed) со всеми ключами ответов; отдельно от HTTP
  exam/                  ЧИСТАЯ логика тестов без БД и HTTP: сборка варианта, проверка, баллы, вердикт КТ
  store/                 ВСЁ общение с PostgreSQL: запросы, транзакции, миграции, защита входа
    migrations/*.sql     версионные миграции (0001_baseline, 0002_..., ...)
  httpapi/               маршруты, middleware, обработчики (без глобального состояния)
  testdb/                встроенный PostgreSQL для интеграционных тестов
```

Зависимости направлены строго вниз: `httpapi → store/auth/exam/content/config`; `exam` зависит только от `content`.
Глобальных переменных нет — всё передаётся через `httpapi.Server`, поэтому слой
целиком тестируется через `httptest`. Каждый метод хранилища принимает `context`
запроса: отмена клиента или таймаут прерывают запрос к БД.

### Конвейер запроса
`request-id → recover → access-log → security-headers → CORS → gzip → маршрут`,
затем на маршруте: `rate-limit → auth` (или `IP-фильтр → rate-limit → ключ` для админки).

## Безопасность

| Угроза | Защита |
|---|---|
| Подделка IP через `X-Forwarded-For` (обход лимитов и `ADMIN_ALLOWED_IPS`) | IP берётся **справа** с учётом `TRUSTED_PROXY_HOPS`; подделанные левые записи игнорируются |
| Перебор пароля | лимит 5 попыток/мин с IP (память) + блокировка на 15 мин по паре «логин+IP» (5 неудач) и по логину со всех IP (50 неудач) — **в БД**, переживает рестарт и работает на нескольких инстансах |
| Блокировка чужого аккаунта атакой | блокировка по паре «логин+IP» — владелец с другого IP входит свободно |
| Перебор существующих логинов | ответ и время одинаковы для существующего и несуществующего логина (фиктивный bcrypt, счётчики по введённому логину) |
| Кража токена | серверная сессия: logout, вход с другого устройства, сброс пароля и удаление аккаунта отзывают токен сразу |
| Перебор `X-Admin-Key` | сравнение SHA-256 за постоянное время, 10 неверных ключей с IP → 429 даже с верным; ключ только в заголовке |
| Слабые секреты | `JWT_SECRET` и `ADMIN_KEY` короче 16 символов — сервер не стартует; предупреждения про `*` в CORS и пустой `ADMIN_ALLOWED_IPS` |
| SQL-инъекции | только параметризованные запросы; динамические имена таблиц — из фиксированного списка |
| Мусор и раздувание БД | коды по маске, `kind` по белому списку, длины/количества ограничены, аватар — только JPEG/PNG/WebP/GIF, проверка base64, тело запроса ≤ 1 МБ |
| bcrypt-усечение на 72 байтах | пароли длиннее 72 байт отклоняются |
| Slowloris | таймауты `http.Server` (заголовки 5 с, чтение 15 с, запись 30 с) |
| Утечка в кэши | все ответы `Cache-Control: no-store`; публично кэшируются только справочники |
| Паника в обработчике | `recover` → 500 без деталей клиенту, стек и `request_id` — в лог |
| Утечка секретов в логи | в лог пишутся метод, путь, статус, длительность, IP; query, заголовки и тело — нет |
| Контейнер | не от root; сборка `-trimpath`; `govulncheck` в CI |

### Тесты: проверка ответов на сервере
Раньше клиент сам собирал вариант, сам считал баллы и присылал готовые `score`/`passed`,
а ключи ответов лежали в публичных JS-файлах и в ответе `/api/tests/{code}`. Теперь:

| Угроза | Как закрыта |
|---|---|
| Подделка результата (`score`, `passed`) | клиент присылает только **ответы**; балл, максимум по блокам, минимумы и вердикт КТ считает сервер; старой ручки `POST /api/results` нет |
| Ответы до прохождения | вопросы уходят **без** `correct/explanations/why/conspect/topic`; ключи возвращаются только в ответе на `submit`; `review` до сдачи — 409. Банки английского и ТГО убраны из публичного `kt.js` (880 КБ → 20 КБ) |
| Выгрузка всего банка | ключи раскрываются только у вопросов сданной попытки; не более 40 попыток в час на пользователя; профильные предметы — только с выданным доступом |
| Подмена состава варианта | вариант собирает сервер и хранит **ссылки** на вопросы (банк, индекс, отпечаток), а не то, что пришлёт клиент |
| Проверка «не тех» вопросов после деплоя | у каждой ссылки отпечаток текста; если банк изменился — 409 «начните заново», а не тихая неверная оценка |
| Двойная сдача, ретраи, гонки | сдача идемпотентна и атомарна (строка блокируется, результат + статистика + отметка «сдана» — одна транзакция); повтор возвращает тот же итог |
| Ответы после окончания времени | у попытки `expires_at` (КТ: 210 мин + 5 мин на сдачу; предмет: 6 ч) — позже 410 |
| Чужая попытка | сдавать и смотреть разбор может только владелец (иначе 404) |

Логика перенесена из `kt.js` без изменений и **проверена на совпадение** с исходным
клиентским кодом: `internal/exam/testdata/gen_parity.mjs` прогоняет оригинальные функции
на тысячах случайных входов, а `go test` требует тех же баллов и вердиктов
(2500 вопросов, 1200 итогов КТ, 1890 порогов предмета).

Что осталось: студент всё равно видит ключи **своих** вопросов после сдачи (это и есть
«Работа над ошибками»), поэтому один платный пользователь при желании может по крупицам
собрать банк за десятки попыток — лимит в час лишь замедляет это. Картинки и аудио
вопросов — публичные статические файлы (их адреса известны из вопроса), но ключей в них нет.
- **Токен в `localStorage`.** Фронт и API на разных доменах (GitHub Pages ↔ Render);
  cookie `SameSite` там не работает. Смягчение: токен отзывается на сервере,
  а XSS на фронте нужно предотвращать отдельно (CSP-мета, экранирование).
- **Один общий `ADMIN_KEY`.** Действия различимы только по IP в audit-логе. При
  появлении нескольких администраторов нужны отдельные учётные записи.

## Масштабирование и производительность

- `LoadUser` — **один SQL-запрос** вместо пяти (мутации на фронте возвращают
  пользователя целиком). `session_id` кэшируется на 15 с, поэтому `auth` не ходит
  в БД на каждый запрос: `/api/me` было 6 обращений к БД, стало 1 (на удалённой
  Neon это главное). Локальный замер (PostgreSQL рядом, 30 параллельных клиентов,
  кабинет с 300 результатами): `GET /api/me` 1617 → 2348 req/s, p99 103 → 45 мс;
  `POST favorites/toggle` 1418 → 2252 req/s, p99 104 → 20 мс.
- Контент тестов (сотни КБ на файл) сжимается **один раз при старте** и отдаётся с
  `ETag` — повторный запрос = `304` без тела; в CPU на запрос сжатие не входит.
- Пул соединений `DB_MAX_CONNS` (по умолчанию 5 — лимит Neon free), индексы на
  `results(user_id)` и журнал, запросы отменяются вместе с клиентом.
- Ошибка БД → `503`/`500`, а не «401 вы не авторизованы»: клиент не разлогинивает
  пользователя из-за сбоя сервера.
- Graceful shutdown по SIGTERM: текущие запросы дозавершаются (деплой Render).
- **Несколько инстансов:** защита входа и блокировки — в БД (работает). Кэш сессий
  и лимитер по IP — в памяти процесса: отзыв сессии на другом инстансе виден не
  позже `SESSION_CACHE_TTL_SEC`, а лимит по IP приблизителен. При росте до нескольких
  инстансов лимитер стоит вынести в Redis; выставите `SESSION_CACHE_TTL_SEC=0`, если
  нужен мгновенный отзыв.
- `GET /api/admin/users` отдаёт всех пользователей без пагинации — при тысячах
  аккаунтов потребуется постраничная выдача.

## Миграции
SQL-файлы `internal/store/migrations/NNNN_name.sql` применяются при старте по
порядку, каждый **один раз, в транзакции, под advisory-lock** (два инстанса при
деплое не гонятся). `0001_baseline.sql` — схема, существовавшая до миграций,
полностью идемпотентна и безопасна на действующей БД.
**Новое изменение схемы = новый файл со следующим номером; выпущенные не править.**
Справочные данные (вузы, специальности, шаги дорожной карты) заливаются
идемпотентно при каждом старте (`store/seed.go`).

## Переменные окружения
См. `.env.example`. Обязательные: `DATABASE_URL`, `JWT_SECRET` (≥16 символов).
Остальные: `KONSPEKT_DIR` (по умолчанию `private/konspekty`), `ADMIN_KEY`, `ADMIN_ALLOWED_IPS`, `ALLOWED_ORIGIN`, `TRUSTED_PROXY_HOPS`,
`DB_MAX_CONNS`, `SESSION_CACHE_TTL_SEC`, `LOG_FORMAT`, `PORT`.

## Запуск и тесты
Нужны Go (версия из `go.mod`) и Postgres (можно бесплатную Neon).
```bash
cd server
export DATABASE_URL='postgres://user:pass@host/db?sslmode=require'
export JWT_SECRET="$(openssl rand -base64 48)"
export ADMIN_KEY="$(openssl rand -base64 24)"
LOG_FORMAT=text go run ./cmd/api
curl localhost:8080/api/ready
```
```bash
go test ./...                          # юнит-тесты, БД не нужна
go test -tags integration ./...        # + интеграционные на настоящем PostgreSQL
```
Интеграционные тесты сами скачивают и запускают PostgreSQL (первый раз ~50 МБ,
запускать не от root). Они проверяют: миграции (в т.ч. одновременный старт
нескольких инстансов), лимиты, каскадное удаление, атомарность, защиту входа,
отзыв сессий, права доступа, админку, поведение при сбое БД и 200 параллельных
запросов при пуле из 5 соединений; для тестов — что ключи не утекают до сдачи (в
ответе и в БД), результат нельзя назначить себе, повторная и параллельная сдача
пишут один результат, чужая попытка недоступна, срок и устаревший контент отсекаются,
КТ собирается как в оригинале (130 вопросов, 16/18/16 английского, 2 целые дорожки). CI (`.github/workflows/server.yml`)
настроен прогонять всё с `-race` и `govulncheck` (локально `-race` не проверялся: нет компилятора C).

## Деплой на Render (Docker)
1. Render → **New → Web Service** → репозиторий, **Root Directory**: `server`, Runtime: Docker
   (или Blueprint из `render.yaml`; `healthCheckPath` там уже задан).
2. Переменные: `DATABASE_URL`, `JWT_SECRET`, `ADMIN_KEY`, `ALLOWED_ORIGIN`.
3. Проверка: `https://<адрес>/api/ready` → `{"status":"ready"}`.

Данные лежат во внешней Postgres и не зависят от редеплоя. Бесплатный план Render
«засыпает» без трафика — первый запрос после простоя будет долгим.

## Известные ограничения
- **Дорожная карта:** шаблон шагов в `store/seed.go` есть только на 2026 год, а
  `handleRoadmap` берёт текущий год — с 1 января 2027 карта будет пустой, пока не
  добавлен шаблон на 2027.
- **Старые результаты** (до перехода на попытки) не имеют разбора — у них пустой
  `attemptId`, в кабинете показывается только итог. Разбор сданной попытки хранится
  90 дней (`store.AttemptRetention`), потом удаляется (результат остаётся).
- **Порядок выкладки:** сервер и фронтенд нужно выкладывать вместе. Старый фронт не
  умеет работать с попытками (его `POST /api/results` и `GET /api/tests/{code}` удалены —
  именно они были дырой), новый фронт не работает со старым сервером.
- В интерфейсе КТ доступен только английский; `de`/`fr` из старого клиентского кода
  были недостижимой демо-заглушкой и не переносились.
- `GET /api/me` отдаёт аватар (до 500 КБ, обычно десятки КБ после сжатия на
  клиенте) в каждом ответе; вынести его в отдельный запрос можно только вместе
  с правкой фронта.
